## 2. Research question

> On CPython 3.13.5 for Linux, does `tarfile` extraction with the explicit `data` filter enforce its documented destination-containment, link, special-file, and metadata-sanitization boundaries across a frozen stateful fixture matrix, while preserving safe data-archive behavior and producing independently auditable filesystem effects?

The unit of analysis is one original synthetic tar archive, one fresh extraction environment, one frozen extraction configuration, and one complete before/after filesystem trace.

The study evaluates one runtime, operating-system family, filesystem environment, filter, error level, fixture grammar, and set of containment invariants. It does not certify Python archive extraction as generally safe, does not test denial-of-service resistance, does not analyze arbitrary third-party archives, and does not authorize extraction outside disposable study directories.

## 3. Externally pinned referent

The normative and operational referents are fixed as:

- PEP 706, **Filter for tarfile.extractall**, final;
- Python 3.13 `tarfile` extraction-filter documentation;
- the live CPython 3.13.5 standard-library implementation available at activation, whose exact source path and file digest must be recorded;
- the documented `data` filter semantics and `FilterError` subclasses.

Primary references:

- `https://peps.python.org/pep-0706/`
- `https://docs.python.org/3.13/library/tarfile.html`

The proposal relies on PEP 706's public-domain or CC0 statement and Python's published documentation. No external archive corpus is required. All formal archives must be generated by original TEMPLEX/0 code from frozen declarative records.

Activation must record:

- Python implementation and full version;
- platform, kernel, architecture, libc, filesystem type if determinable without elevated access, current umask, and symlink capability;
- `tarfile` module path and SHA-256;
- availability of `data_filter` and the relevant exception classes;
- exact documentation URLs and retrieval date;
- whether vendor or security patches alter the runtime behavior from upstream CPython expectations.

A runtime change from CPython 3.13.5 closes activation as NO-GO unless the proposal is first replaced in a separate portfolio cycle. The study must not silently migrate to Python 3.14's changed default.

## 4. Frozen hypotheses

### H1 — destination containment and protected rejection

For every protected path or link fixture extracted with `filter="data"` and `errorlevel=1` into a newly created destination root:

1. no filesystem node outside the destination root changes;
2. no resolved extracted path escapes the destination root;
3. every member whose documented semantics require refusal raises the corresponding `FilterError` class at the first protected offending member;
4. any partial in-root extraction before refusal is fully represented in the trace and never treated as transactional rollback.

Protected refusal classes must include, when representable on the pinned platform:

- absolute member path;
- member path resolving outside the destination;
- absolute symbolic-link target;
- symbolic-link target resolving outside the destination;
- absolute hard-link target;
- hard-link target resolving outside the destination;
- FIFO or other special-file member rejected by `data_filter`.

**Support criterion:** zero outside-root changes, zero unreported partial effects, and exact expected refusal class for every protected fixture.

### H2 — stateful containment under member order and pre-existing nodes

For every frozen stateful sequence involving only disposable study paths:

1. a pre-existing in-destination symlink must not enable a later member to change a node outside the destination;
2. an archive-created link must not pivot a later member outside the destination;
3. reordering members may change which in-root members exist before refusal, but must not change the outside-root containment result;
4. duplicate names and later overwrites must remain inside the destination and be recorded exactly;
5. the independent filesystem oracle must agree with the harness on every changed, created, replaced, linked, or removed node.

**Support criterion:** zero outside-root changes and complete oracle/harness agreement across the full frozen stateful matrix.

This hypothesis does not require duplicate-name rejection because the Python documentation explicitly notes that later archive members may overwrite earlier ones.

### H3 — safe-control preservation and metadata normalization

For every frozen safe data archive:

1. all expected regular-file bytes and directory structure are extracted;
2. every permitted internal link resolves to the expected in-root target;
3. regular-file modes, executable bits, ownership fields, directory modes, and other metadata match the documented `data_filter` transformations;
4. no safe fixture raises a filter error;
5. two clean executions produce the same normalized filesystem projection and event trace.

**Support criterion:** zero false refusals, zero content mismatches, exact normalized metadata agreement, and byte-identical canonical traces across two clean runs.

A safe control is defined by the frozen fixture manifest and must not be added after protected outcomes are inspected.

## 5. Frozen behavioral domain

### 5.1 Archive format

- Uncompressed POSIX tar is the primary transport to avoid compression metadata as a confound.
- Python `tarfile` creates the bytes from declarative fixture records.
- PAX extended headers may be used only for explicitly frozen long-name fixtures.
- GNU sparse files, encrypted containers, multi-volume archives, and malformed checksum experiments are outside the primary hypotheses.
- No archive may contain payloads intended to execute code.

### 5.2 Extraction configuration

The primary configuration is fixed as:

- `TarFile.extractall(path=destination, filter="data")`;
- `errorlevel=1`;
- a newly created destination directory unless the fixture explicitly freezes a pre-existing in-destination node;
- a sibling sentinel root used only to detect outside-destination changes;
- process working directory inside a disposable study root;
- no elevated privileges;
- no global mutation of `TarFile.extraction_filter`.

Default extraction without an explicit filter may be run only as a small descriptive control after all primary artifacts and expectations are frozen. It may not affect H1–H3.

### 5.3 Filesystem projection

Before and after extraction, the oracle must project the disposable study tree into canonical records containing, as applicable:

- relative path from the study root;
- node type;
- lstat mode;
- size;
- SHA-256 for regular-file bytes;
- symbolic-link target text;
- hard-link identity under a frozen inode-equivalence representation;
- modification time normalized or excluded according to a rule frozen in Cycle 1;
- whether the node is inside destination, inside sentinel, or elsewhere inside the disposable root.

No path outside the disposable root may be intentionally created, modified, or used as a fixture target.

### 5.4 Fixture families

Cycle 1 must freeze a declarative grammar and exact manifest containing at least the following families:

1. safe regular files and nested directories;
2. safe internal symbolic links;
3. safe internal hard links;
4. leading slash and platform-recognized absolute member names;
5. `..` path components and normalized outside-destination paths;
6. absolute and outside-destination symbolic-link targets;
7. absolute and outside-destination hard-link targets;
8. FIFO or another non-device special member constructible without privileged host operations;
9. pre-existing in-destination symlink pivot sequences;
10. archive-created link pivot sequences;
11. duplicate-name overwrite sequences;
12. safe metadata-sanitization controls;
13. member-order permutations for selected protected sequences.

The manifest must freeze every member's type, name, link target, mode, payload digest, order, expected filter disposition, expected first refusal index, and expected outside-root effect count before formal extraction.

### 5.5 Explicit exclusions

The primary study excludes:

- resource-exhaustion and decompression-bomb testing;
- races with an external process mutating the destination during extraction;
- Windows path and reparse-point semantics;
- case-insensitive filesystem behavior unless the activation environment itself is case-insensitive;
- network filesystems;
- mount points, bind mounts, containers, chroots, namespaces, or privileged sandboxing;
- arbitrary external tar files;
- claims about `zipfile`, `shutil.unpack_archive`, GNU `tar`, BSD `tar`, or non-CPython implementations.

## 6. Independent filesystem oracle

The primary oracle must not call `tarfile.data_filter` or reuse the extraction harness's verdict helpers.

It must:

1. snapshot the disposable study tree before extraction;
2. snapshot it after success or exception;
3. compute the exact node-level diff;
4. resolve every changed node's containment using paths derived from the actual filesystem state;
5. verify sentinel bytes and metadata independently;
6. compare observed refusal type and member index with frozen expectations;
7. emit a canonical machine-readable record.

The oracle may use standard-library filesystem calls such as `os.lstat`, `os.readlink`, `os.stat`, `pathlib`, and `hashlib`. It must not infer safety solely from archive member names.

### 6.1 Hand-audited correctness gate

Before the complete manifest is executed, Cycle 2 must freeze and run at least twelve miniature fixtures with manually stated before/after projections. They must cover:

- one safe regular file;
- one safe nested directory;
- one safe internal link;
- one absolute member path;
- one `..` escape;
- one absolute link target;
- one relative outside link target;
- one special file;
- one pre-existing symlink pivot;
- one archive-created link pivot;
- one duplicate overwrite;
- one partial-extraction sequence with a safe prefix and rejected later member.

The oracle and harness must agree with all frozen expectations. At most one bounded correction cycle is permitted before the complete formal matrix.

## 7. Harness and event trace

The extraction harness must record:

- fixture ID and manifest digest;
- archive SHA-256 and member count;
- extraction configuration;
- destination and sentinel paths represented only by normalized placeholders in canonical output;
- every member in order;
- success or exception;
- exception class, message category, and associated member;
- canonical before and after projections;
- exact filesystem diff;
- outside-destination change count;
- safe-control content and metadata checks;
- runtime and source identities;
- elapsed time as non-deterministic metadata excluded from the scientific digest.

Absolute temporary paths must not enter the portable scientific payload. Raw operational logs may preserve them separately.

## 10. Disposition rules

### Full bounded success

All of the following must hold:

- activation and permission preflight passes;
- the runtime and filesystem match the frozen domain;
- the hand-audited correctness gate passes;
- H1, H2, and H3 are supported;
- zero node outside the destination root changes in any protected fixture;
- complete canonical scientific results reproduce byte-identically;
- the study closes within four approval cycles.

### Partial result

The study is partial if the setup and oracle gates pass and the complete matrix is valid, but one or more of H1–H3 is unsupported or unresolved without invalidating the remaining evidence.

### Negative setup result

The study closes before formal extraction if:

- the pinned runtime or required filter API is unavailable;
- symlink or hard-link fixtures cannot be represented safely in the disposable environment;
- the filesystem oracle cannot establish reliable before/after identity;
- the hand-audited gate fails after the single permitted correction opportunity;
- safe containment cannot be guaranteed without privileged or externally managed sandboxing;
- documentation or implementation identity cannot be frozen.

### Operationally incomplete

The study closes as operationally incomplete if complete results and one clean reproduction cannot be produced within the cycle and resource caps. Partial output may be preserved but must not be represented as a complete corpus result.

## 11. Resource and cycle limits

From activation through closure, Study 006 has a maximum of **four approval cycles**:

1. activation, environment freeze, active protocol, fixture grammar, projection schema, and exact manifest;
2. generator, independent oracle, hand-audited gate, and frozen instruments;
3. complete formal matrix execution and artifact preservation;
4. clean reproduction, analysis, final report, and closure.

No fifth cycle may be added.

Before any formal execution, the active protocol must freeze conservative caps for:

- fixture count;
- members per archive;
- payload bytes per member and per archive;
- total extracted bytes;
- filename and link-target length;
- wall-clock time per fixture and for the complete matrix;
- process address space where supported;
- number of filesystem nodes.

The study must remain standard-library-only. It may not use paid services, external compute accounts, private data, secrets, third-party repositories, elevated privileges, real user directories, or untrusted external archives.

## 12. Verification requirements

Every applicable cycle must verify:

- exact live Git blob identity for committed scientific source before use;
- deterministic regeneration of manifests and archives;
- safe-root path assertions before extraction;
- complete before/after filesystem projections;
- no outside-root changes;
- targeted unit tests;
- compile verification;
- canonical result reproduction;
- separation of portable scientific payloads from absolute execution-path metadata.

A committed file is not evidence that its bytes were executed. Source identity must be computed directly.

## 13. Human and external boundaries

No human playtest, subjective scoring, external communication, defect report, vulnerability disclosure, or third-party repository operation is part of this proposal.

If a protected fixture appears to reveal a previously unknown CPython security defect, TEMPLEX/0 may preserve the evidence privately inside the authorized project environment and stop. Public issue filing, external contact, disclosure timing, or publication beyond the existing repository requires a separate explicit human-reviewed authorization.

## 14. What would be learned

A positive result would show only that the explicit Python 3.13.5 `data` filter and the frozen harness preserved the documented boundaries across the exact Linux fixture matrix.

A negative result would identify a concrete archive, member sequence, runtime identity, filesystem state, expected documented boundary, observed exception or effect, and reproducible before/after trace.

A partial result would separate filter behavior, oracle validity, safe-control preservation, and stateful containment rather than collapsing them into a single security claim.

None of these outcomes would establish that tar extraction is safe for arbitrary untrusted input.
